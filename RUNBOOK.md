# Runbook: how the Kingdom Hearts Final Mix decompile is done

For the owner and any agent (Claude or the local Qwen). Local work only: nothing is pushed anywhere.

## 1. The goal and the one rule that proves progress

The game's program (`SLPS_251.98`, Final Mix, from the owner's disc) is about 7,000 functions of PS2 machine
code. The job is to write C for each function that the game's own 2001 compiler (ee-gcc 2.96) turns back into
**exactly the same bytes**. That's a *matching* decompilation.

Proof is mechanical: the build links everything (C plus the assembly not done yet) into one program and checks
its SHA-1 against the original. The last line of a build must be:

```
build/fm/SLPS_251.98.rom: OK
```

If a function's C is even one instruction off, that line says FAILED. Nothing is committed unless it says OK.

## 2. How the pieces fit

| Piece | What it is |
|---|---|
| `src/**/*.c` | The C. A function not done yet is one line: `INCLUDE_ASM("asm/nonmatchings/<file>", <name>);` which pulls in its assembly. |
| `asm/nonmatchings/<file>/<name>.s` | Each function's original assembly, generated by `configure.py` (splat) from the program file. Not in git. |
| `config/kh.fm.yaml` | The layout of the program: which address range is which file (`c`), plain assembly (`asm`), data, read-only data. |
| `config/fm/*.txt` | Names at addresses. `jp_names.txt`: upstream's names (which are JP addresses, e.g. `func_00112190`) placed at their Final Mix addresses. `fm_names.txt`: Final Mix address names used directly by C. |
| `configure.py` | Writes the build rules. Per-file compiler settings: `STRICT_ALIASING_FILES` (files built with strict aliasing; all others get `-fno-strict-aliasing`), `NO_G_FILES` (files built without `-g`), and the Final Mix mode of `tools/masps2.py` (no extra `nop`s). |
| `wsl-build.sh` | The PS2 compilers are 32-bit Linux programs that can't read the Windows drive, so every build runs in a copy inside WSL (`~/kh1-decomp-build`, or `~/kh1-build-<worktree>`), and the generated `asm/` is copied back. |
| `agent-tools.sh` | The helper every agent uses: `configure`, `build`, `list`, `asm`, `m2c`, `diff`. |
| `MATCHING.md` | The rules and every trick that made functions match (read it). |
| `notes/<agent>.md` | Each agent's notes: struct layouts, patterns, functions given up on with their closest C. |
| `eu-notes/` | The tools that mapped upstream's JP C onto Final Mix and EU, and `fm_followups.md` (known problems). |

Versions: upstream's C was written for the Japanese original. This copy also builds **Final Mix** (`fm`, the main
target) and **EU** (`eu`, on branch `eu-stage1`, to be caught up later). One set of C files serves all; where a
version differs, markers choose:

```
#ifdef VERSION_FM                     Final Mix's code differs: FM uses this; JP/EU use the #else part
...C or INCLUDE_ASM for FM...
#else
...JP's C...
#endif

#ifdef VERSION_FM                     a function only Final Mix has (names start fm_func_)
INCLUDE_ASM("...", fm_func_X);
#endif
```

## 3. Who does what

* **The coordinator** (Claude, main session): config and build changes, merging agents' branches into `fm`, fixing
  missing names after merges, deciding file assignments. Agents never edit `config/`, `configure.py`, `tools/`,
  `include/` or `eu-notes/`.
* **Agents** (Claude subagents, or Qwen): each works in its own git worktree under
  `C:\Users\you\psp-learning\kh1-study\kh1-wt\` (`a1`..`a6`, `q1` for Qwen) on its own branch (`fm-a1`.., `fm-q1`),
  on its own list of C files, so they never collide. Each commits one function at a time.
* Merging: the coordinator runs `git merge fm-<agent>` in the main folder, builds, adds any missing names
  (`config/fm/fm_names.txt`), and commits. Then the agent's worktree is fast-forwarded to `fm` before its next run.

Qwen's files and worktree are in `AGENTS.md` (OpenCode reads it automatically).

## 4. Matching one function, in detail

1. **Pick.** `wsl -e bash ./agent-tools.sh list <file>` lists the file's assembly functions, smallest first
   (size in bytes). Take the smallest you haven't tried (check your notes file for give-ups).
2. **Read the assembly.** `asm <file> <func>`. Registers: arguments in `$4`-`$7` (a0-a3), float arguments in
   `$f12`, `$f14`; return value in `$2` (v0) or `$f0`. `jal func_X` is a call; `lui` + `%lo(D_X)` is a global.
   `jr $31` is return; the instruction after a branch or jump (the delay slot) runs before it.
3. **Draft.** `m2c <file> <func>` prints a first draft of C from m2c, using the file's types. It is a starting
   point; check it against the assembly.
4. **Write.** Replace the `INCLUDE_ASM(...)` line with the function. Reuse the types and prototypes the file
   already has (grep `src/` and `include/` for the function and global names). Add any new prototype or struct near
   the top of the same file.
5. **Build.** `build`. Then:
   * last line `build/fm/SLPS_251.98.rom: OK` → it matches; commit (step 7).
   * a compile error → fix it.
   * FAILED → `diff <func>` shows the original (left) and yours (right) side by side; adjust and rebuild.
6. **Give up** after about 6 failed builds: `git checkout -- src/<file>.c` (safe because every match is committed
   straight away), and add the function to your notes file with your closest C and what still differs.
7. **Commit.** `git diff --stat` must show only that one file. Then
   `git add src/<file>.c` and
   `git commit -m "Match <func> (<file>)"`. One function per commit.

### What usually fixes a mismatch (more in MATCHING.md)

| The diff shows | Try |
|---|---|
| two `li` swapped, or `movz` vs `movn` | flip the condition or swap the ternary arms |
| registers different, instructions the same | reorder declarations; reuse a variable; add a missing prototype for a called function |
| stores in a different order | the compiler emits the last store first, then the rest in source order; permute statements |
| a value reloaded after a store in the original, not in yours | in strict-aliasing files, read it through a union or type the field as `s32` |
| `lui`/`addiu` then `sw 0(reg)` for a global used once | the global is `volatile` |
| `j func` (tail call) where the original has `jal` + return | make the function return `s32`, or wrap the call in `do { f(); } while (0);` |
| extra sign-extension (`dsll32`/`dsra32`) on a u64 test | cast first: `(s32)(x >> n) & 1` |
| float constant off by one bit | write more digits (`3.1415928f`) and check the hex |

## 5. Tools beyond the basics (Claude agents use these; optional for Qwen)

* **Sandbox compile**: compile one test C file in the WSL mirror with the file's exact flags and compare its
  instructions with the target, many variants per minute (scripts in each Claude agent's scratch folder, described
  in notes/a4.md, a3.md, a5.md).
* **Statement-order brute force / hill-climb**: generate every order of 5-9 statements (or move one line at a time)
  and compile them all; pick the one that matches (a2's hc.py, a4's cmp.py).
* **VU0 inline helpers**: hand-written vector-unit sequences match as `static inline` functions with
  `__asm__ volatile` (templates in notes/a2.md).

## 6. Known limits

* Functions whose `jr` delay slot holds a vector-unit store (`sqc2`), or whose last VU0 instruction sits in it,
  were hand-written in assembly: leave them.
* A few functions take arguments in unusual registers (`$v0`): leave them.
* GCC 2.96 sometimes compiles `xhumungus` functions 4 bytes longer after unrelated edits (see
  eu-notes/fm_followups.md); if a build fails with a clean diff in your function, try committing other functions
  first.
