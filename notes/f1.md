## Rules found (23 Nov, f1)

F1. **Defining one function in C can change a DIFFERENT, already matched function far away in the same file, with
    no call relation at all** (func_0013C548 at line 740 broke func_001560F8 at line 3308: combine stopped folding
    `sb $0,D_00550400+3($3)` and the function grew 8 bytes, shifting everything after it).
    The RTL before combine is identical; which way it goes flips with ANY extra declaration anywhere above
    (`extern int dummy;` flips it, blank lines don't), so it depends on the compiler's memory layout
    (ee-gcc 2.96 leaves rtx fields uninitialised / hashes by pointer), not on the C of the victim.
    How to find the victim: keep the bad build's map, build the clean tree, `diff` the two
    `build/fm/SLPS_251.98.map` files: the first function symbol whose address moves comes right after the victim.
    Fix: express the same thing with a different set of declarations. Here: instead of an extra
    `s32 f_r(...) __asm__("f")` alias, change the file's real prototype of the callee to return s32
    (one declaration less; the other caller still matched). If nothing natural works, any extra harmless
    declaration above the victim flips it back.
    Scripts: fable-work/chk60f8.sh (grep one instruction in the compiler output), dump.sh + fx.sh (per-pass RTL
    dump of one function, good vs bad).

F2. **Walking pointer and base pointer in each other's registers (base stays in the parameter's register, the
    walker gets a new one, loop counts DOWN 9..0 with bgezl): write the loop as an index loop, not a pointer walk.**
    `p += off; for (i = 0; i < 10; i++) if (*(s32*)(p + i*4 + 8) - *(s32*)(p + i*4 + 4) > 0) f(p + *(s32*)(p + i*4 + 4));`
    The compiler makes the walking pointer and the down-counter itself (strength reduction), and then the base keeps
    its register. A hand-written `e = p; ... e += 4` with `for (i = 9; i >= 0; i--)` gives the swapped registers.
    Also fixed the load order (`lw 0x10` before `lw 0xC`): write the condition with both loads spelled out
    instead of a saved `off` variable. Proven by func_001560C8.

F3. **THE MECHANISM BEHIND RULE 1 (bne vs bnel next to a call) is "cannot throw", and it can be switched on
    from a declaration: `NOTHROW(void, callee);` (macro in include/common.h).**
    ee-gcc 2.96 sets TREE_NOTHROW on a function after compiling its body (if nothing in it can throw), and every
    later call to it in the file gets a `REG_EH_REGION 0` note (visible with -dr: the call to a C-defined callee
    has `(expr_list:REG_EH_REGION (const_int 0))`, a call to a declared-only one has no note = "may throw").
    Reorg treats the two differently, hence plain vs likely branches around the call.
    Consequences:
    - What the callee's body contains does not seem to matter (C has no exceptions, so every compiled body gets
      the flag): func_00218DD0 calls into other files and its caller func_002190C0 still wants it flagged.
    - Target plain, callee in ANOTHER file (the split is finer than the original source) or still INCLUDE_ASM:
      write `NOTHROW(void, callee);` instead of its prototype. No need to match the callee first.
      It is an `extern inline` dummy body (compiled far enough to get the flag, never emitted) with an old-style
      `double` parameter so that inlining fails at each call and a normal `jal` is emitted.
      Not for callees with float arguments (no prototype = promoted to double).
    - A likely branch in the target does not prove the callee was unflagged: func_002479A0 keeps its one
      `beql` with every callee NOTHROW. So when unsure, flag all callees that sit at lower addresses in the
      same original file and see.
    Proven by xpackage func_00247A30 and func_002479A0 (a3/a4 "known reorg beql-vs-beqz problem"); their callees
    live in src/xmonitor.c, so xmonitor.c and the start of xpackage.c were one source file originally.
    Also xpotato func_002190C0 (task E) without matching func_00218DD0 first.
