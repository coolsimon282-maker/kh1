# Agent a2 notes: src/xaudacity.c (Final Mix)

166 functions matched, one commit each. 7 left, all blocked by tooling or a compiler difference (see below).

## What the module is

xaudacity.c is a table of small script/command handlers. Every handler is `void f(XAudArg* arg0)`: `arg0` is an
argument array (each slot an s32, f32 or pointer) and the result goes back into `arg0[0]`. Most handlers are thin
wrappers: they call one engine function with `arg0[0..n]` and store the return value in `arg0[0]`. `arg0[0]` is
usually an actor/object pointer (`XAudObj`, laid out at the top of the file).

## Types (top of src/xaudacity.c)

- `XAudArg`: a union {s32 s; u32 u; f32 f; void* p; XAudObj* obj; XAudPtrs* ptrs; XAudFlags0* flags; XAudB8* b8}.
- `XAudObj`: the object. Known fields: 0x010 vec, 0x02C parent XAudObj*, 0x030 vec, 0x06C ptr (0xBD u8, 0xCC f32
  angle), 0x088 flags, 0x0D0 matrix, 0x120 vec, 0x130 ptr (0x18 f32, 0x4C/0x4E u16, 0x58/0x59/0x5A u8), 0x14C ptr,
  0x150 f32 (yaw, from atan2f(x, z)), 0x164, 0x178, 0x1CC flags (|= / &= ~), 0x1DC offset table, 0x284 f32,
  0x370 u64 flags (`XAud370` union: raw + bitfields), 0x398 ptr, 0x39E u8, 0x3A4/0x3A8/0x3AC flag words,
  0x3B0, 0x3C0 vec, 0x3D0, 0x3D4 f32, 0x3E4, 0x450 vec, 0x490 vec.
- A prototype goes right above the first function (in file order) that uses it. An implicit declaration followed
  by a later prototype is a "conflicting types" error.

## Patterns that matched

- Tail-call wrappers (`addiu sp; sd ra; ... j func`) are just `func(arg0[0].s, arg0[1].s);`. Float arguments need a
  real prototype with `f32` (they go in $f12/$f13). EE ABI puts int and float arguments in separate registers, so
  read the order from the registers (e.g. $4, $f12, $5 = `(s32, f32, s32)`).
- Reading one bit of a u64 into an s32 or testing it: write `(s32)(x >> n) & mask`, **not** a bitfield and not
  `(x >> n) & mask`. Both of those add a `dsll32/dsra32` sign-extension. `dsll k; dsra32 0; andi` in the target is
  `(s32)(x >> (32-k)) & 1`.
- Writing bits of a u64 (`lwu` + `andi` + `dsll` + `or` + `sd`): a u64 bitfield assignment (`p->bits.f = arg0[1].u`).
- Setting bits: `raw |= 0x...` on the u64 works.
- `if (x) a = 1; else a = 0;` vs `if (!x) a = 0; else a = 1;` flips `beqz`/`bnezl`. Pick the one with the
  target's branch sense.
- func_00129E18: with `if (x == 0) {r = 1} else {...}` and a local copy of the global, the `b` and the `ld`
  order both matched.
- Local vectors and matrices: `f32 v[4] __attribute__((aligned(16)));` / `f32 m[4][4] __attribute__((aligned(16)));`.

## Left / given up

- func_00129CC0, func_00128F58, func_00128E28, func_00128E80: **tooling bug** in tools/masps2.py. They compute
  `(x / 180.0f) * PI`, and gcc emits `li.s $fN` followed directly by its own `nop` (the div.s hazard).
  `get_op_inputs("nop")` then fails on `op, args = op.split()[:2]` (ValueError). Closest C (untested because of
  the crash): func_00129CC0 `arg0[0].obj->unk_06C->unk_CC = (arg0[1].f / 180.0f) * PI;`; the other three have
  JP C in comments in the file. A fix that makes `get_op_inputs` return [] for an op with no arguments would
  probably unlock all four. (func_00129188/func_00129058/func_001290C8 use the same constants but matched,
  because there `li.s` isn't followed by a bare `nop`.)
- func_0012AE28, func_0012A548: the target uses `cvt.w.s` (shown as .word) and has no nop after `mfc1`. Our gcc
  emits `trunc.w.s` and masps2 always adds a nop after mfc1. Closest C for AE28: `s32 n = arg0[0].f * 4.0f;
  func_001EE618(0, 0, n); func_001EE618(1, 0, n);` (only the extra nop differs). A548 converts three floats with
  `(u16)((v[i] / (2*PI)) * 65536.0f)` into an s32[3] at `arg0[0].ptrs->unk_04`.
- func_0012AEB8 (raycast step loop): the structure matches, but the target has no nop after `c.lt.s` or after
  `mtc1 $0,$f20` + `lwc1`, while masps2 always adds them. It looks like a different compiler mode. Closest C:
  a local struct (pos[4] @0, step[4] @0x10, f32 @0x20/0x24, s32 @0x28, flags @0x30, out[4] @0x40, size 0x80)
  plus dir[4]; `func_00116660(&ray)`, a loop with `sceVu0ScaleVector` and `func_001166E8(&ray)` while
  `dir[3] > 0`, then `arg0[0].s = ray.unk_30 & 1`.

## Big findings (apply to the whole ppp library)

* **Hand-written VU0 code is matchable with inline asm.** The "Handwritten function" ppp files use small VU0
  macro sequences. Writing them as `static inline` functions with `__asm__ volatile` reproduces the code exactly
  (gcc picks the same registers). The three seen so far:
  - random float in [0,1): `addi $8,$0,-1; qmtc2.ni $8,$vf2; 5x (vrxor R,$vf2x; vrnext.x $vf1,R); vitof0.x
    $vf2,$vf2; vadd.x $vf1,$vf1,$vf2; qmfc2.ni %0,$vf1` with `"=r"(f32 r)` and clobber `"$8"` (see
    src/ppp/eiProg/pppRandFloat.c `vu0Rand`).
  - v.xyz *= s: `qmtc2.ni %1,$vf9; lqc2 $vf10,0(%0); vmulx.xyz $vf10,$vf10,$vf9x; sqc2 $vf10,0(%0)` with inputs
    `"r"(ptr), "r"(f32)` (pppKeMatPht.c `vu0ScaleXYZ`). 36 functions in asm/ use this sequence.
  - sqrt: `qmtc2.ni %1,$vf2; vsqrt Q,$vf2x; vwaitq; vaddq.x $vf2,$vf0,Q; qmfc2.ni %0,$vf2` (pppEiWindFun.c).
  Copy the helper into each file (can't add it to include/).
* **The ppp code behaves as if compiled with -fno-strict-aliasing.** Several targets reload `ppvPObj.next`, a
  global count, or a struct field after a float store; compiling the same C in the sandbox with
  `-fno-strict-aliasing` gives the target exactly (checked on pppRyjDrawMatrixWorldNoRotCalc and
  func_0019F810). Compiling every matched ppp file with and without the flag gives identical code, while
  xhumungus.c, xtrumpet.c and xbuffalo.c change, so it looks like the ppp library was built with different
  flags. Until the build does that per directory, the workaround is reading the value through a one-member
  union (alias set 0), e.g. `typedef union { pppPObject* next; } PObjNext; #define NEXT
  (((PObjNext*)&ppvPObj)->next)`. Works both ways, so it stays correct if the flag is added later.
* `ppp.h`'s include guard is broken (`#ifndef PPP_H` / `#define PPP`): including both "ppp.h" and
  "ppp/pppUtil.h" gives "conflicting types". Include only "ppp/pppUtil.h" when you need its prototypes.

## Patterns that matched (second run)

* pppRand*Calc family: `if (pobj->time == 0) { r = rand...; *rv = r; } else { if (p->cdt.time != pobj->time)
  return; rv = ...; }` then `if (p->index != -1) tgt = &val[index]; else tgt = &ppvDbgTemp;` (that order gives
  the target's `beq`). Up = `(r + rand) * 0.5f`, Down = `r = rand; r = -r; if (twice) r = (r - rand) * 0.5f;`.
  Char/Short/Int: `*tgt += (s32)(f32_expr)`; u8/u16/u32 scale.
* Separate bit tests on a u64 (`andi 0x200; andi 0x100; beqzl; bnezl`) need nested ifs:
  `if (f & 0x100) { if (!(f & 0x200)) {...} }`; `&&` gets folded into `(f & 0x300) == 0x100`.
* `D[n] = e; n++;` (not `D[n++] = e`) gives the target's `addiu` before `sll`.
* Flags built as `flags = 0; if (a) flags = 1; if (b) flags |= 2; if (c) flags |= 4;` give `sltu/ori/movn`
  straight into the argument register.
* Locals for values that are both stored and used (`len = v->len = p->len;`) stop the reload after the store.
* Byte flags written with plain u8 ops (`v->stt |= 1`, `&= ~1`) but read through a u8 bitfield (`andi 1; andi
  0xff`) in pppKeHitBornCalc: a union of the u8 and the bitfield struct.
* func_0019F698 is a plain recursive quicksort (largest pos[3] first); gcc turns the second recursive call into
  the outer loop by itself, so write both calls.
* Loops over 3 rows with a call inside are not unrolled; write `for (i = 0; i < 3; i++)` and gcc gives the
  target's count-down loop. `3.1415926f` is 0x40490FDA (3.1415925f is ...D9).
* Two adjacent s32 fields tested together with one `ld` came from `*(u64*)&p->rot[0] != 0 || p->rot[2] != 0`.

## Patterns learned (third run)

* **Float to unsigned**: `(u16)(s32)(f)` gives a plain `cvt.w.s`; `(u16)(f)` alone gives gcc's unsigned
  conversion (`c.le.s` against 2^31, `sub.s`, `or 0x80000000`). For u8 fields filled from floats
  (pppKeLnsFlsDraw) the unsigned form is what the target has.
* **xaudacity aliasing**: func_0012A548 reloads both the destination pointer and the source floats after
  every store; going through `XAudArg*` (the s32/f32/pointer union) for both sides gives exactly that.
* **-fno-strict-aliasing helped**: pppRyjLightCalc matched first try with the C from the notes once
  src/ppp/ was built with the flag (no union workaround needed).
* **More hand-written VU0 helpers** (same `static inline` + `__asm__ volatile` approach, input `"r"(ptr)`,
  output `"=r"(f32)`, clobber `"memory"`):
  - normalize-in-place returning the old length (pppEiWfacc.c `vu0NormalizeLen`): `lqc2 $vf10; vadd.xyz
    $vf8,$vf0,$vf10; vmul.xyz $vf10,$vf10,$vf10; vmove.xyz $vf9,$vf10; vaddx.y; vaddy.z; vsqrt Q,$vf9z;
    vwaitq; vaddq.x $vf10,$vf0,Q; qmfc2.ni %0,$vf10; vdiv Q,$vf0w,$vf10x; vwaitq; vmulq.xyz $vf9,$vf8,Q;
    sqc2 $vf9`.
  - length of a vector (pppRyjMegaBirthModelFilter.c `vu0Length`): `lqc2; vmul.xyz; vaddx.y; vaddy.z;
    vsqrt Q,$vf10z; vwaitq; vaddq.x; qmfc2.ni`.
* **Float constant spelling**: gcc 2.96 parses `0.05f` as 0x3D4CCCCC (one ulp low); writing the exact
  value `0.049999997f` gives ...CB. Write the "round" decimal the programmer would have written.
* **Statement-order search pays off for parameter-block fillers**: pppKeLnsFlsDraw only matched after
  trying every position of two of the stores (scheduling + register choice follow source order). I used a
  small hill-climb script (permute the statements between two marker lines, compile in the WSL mirror,
  count differing words); worth doing for the DrawMdl* family too.
* **A call with an extra zero argument**: an unexplained `daddu $5,$0,$0` before a call is a second
  argument (`KeLnsFls_Draw(&info, 0)`).
* **Switch without jump table** (pppKeZCrct/Shp): small `switch (u8)` with cases 0..3 compiles to the
  beq/slti tree; cases with identical tails are cross-jumped by gcc itself, write them out in full.
