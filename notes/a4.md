## Things learned

* **The scratchpad folder is shared with other agents**: keep sandbox files in your own subfolder, never
  in its root (my first `cc.sh`/`t.c` there were overwritten mid-session).
* **Sandbox compile.** Compiling a test .c directly in the WSL mirror is much faster than a full build and
  shows the exact output (`-O2 -G0 -g -DVERSION_FM`, piped through `tools/masps2.py`):
  `cd ~/kh1-build-a4 && tools/cc/ee-gcc2.96/bin/ee-gcc -c -B tools/cc/ee-gcc2.96/bin/ee- -Iinclude -isystem include/sdk/ee -isystem include/gcc -DVERSION_FM -O2 -G0 -g _t.c -S -o - | python3 tools/masps2.py`.
  Put many variants (or all permutations of a statement order) in one file and grep the result.
* **masps2.py always adds a `nop` after `mfc1`, `c.le.s`/`c.lt.s`, and after `mtc1` followed by a float op.**
  FM's own code often has no nop there (e.g. float->int `cvt.w.s; mfc1; sll`), so those functions can't match
  with the current tool chain. Check the target for `mfc1` followed directly by another instruction before
  starting one. (Seen in: fm_func_00111BE8, func_0018B5E8, func_00189F20, func_0018A680.)
* Store order: gcc schedules `a=0; b=0;` as `sw b; sw a` (last one first, the rest in order, the first ends
  in the delay slot). Chained `a = b = c = 0.0f` gives `s.s a` first, then the rest from the end backwards.
* `x % C` after an unused `x / C` (hours/minutes/seconds from a frame count) leaves a dead `move` of the
  divisor: that's how fm_func_00111B48/B90 matched (compute the unused quotient too).
* Loop with a pointer reloaded every iteration plus a reversed counter: write the offset as its own
  variable (`ofs += 2`) with a `u8*` base (func_00128DC0).
* gcc's own delay-slot choices in the `-S` output don't matter (the assembler redoes them), but branch-likely
  (`bnel`) does: if the target has `bnez` + a load in the delay slot where gcc gives `bnel`, no loop form
  tried changes it (func_001C1AE0).
* A `void` function ending in a call always becomes a tail call (`j`); a target with `jal; nop; ld ra; jr`
  needs something else (not found: variadic, struct return, u64 return all still tail-call or differ).
* `((Vec*)&D->unk_10 + i)->x` (pointer arithmetic on a cast) gives `addu v0,a0,v0; lwc1 0x10(v0)`, while
  `D->vec[i].x` gives `addu ...,16` separately (func_001113A8).

## Data names used in shared (not `#ifdef VERSION_FM`) functions

These functions are in code shared with JP/EU, but their globals aren't in `config/fm/jp_names.txt`, so the C
uses the FM-address names. They build for FM; for EU/JP they'd need the JP names added to the name lists:

* xbuffalo `func_001C1868`, `func_001C1A90`, `func_001C1AB8`: `D_0037A168`, `D_0037A16C` (JP probably
  `D_003759D0`/`D_003759D4`); `func_001C2110`: `D_0037A178` (the 4 words fm_func_001C07A8 clears).
* ppp/ryjProg `pppRyjDrawMatrixWorldFrontCon`, `pppRyjMatrixWorldXZYCon`, `pppRyjMatrixWorldZYXCon`: `D_003701D0`
  (a zero/origin vector), `D_003701E0` (a zero angle).
* xcream `func_00128DC0`, `func_00128DF8`: `D_00514F10` (JP 4 bytes before `D_0051C6C4`).
* xpackage `func_00247CD8`: `D_00469FC8` (function table); `func_00247D18`: `D_00491878`, `D_00491880`
  (strings for the empty assert-like `func_00247D88`).
* xcream `func_00128488`: `D_004F82C0`, `D_004F8270`.
* xtrumpet `func_00111468`, `func_00111408`: `D_002BCB68` (8 bytes after `D_002B90B0`).

xpackage's `D_00663A28` (defined in xpackage.c) is `D_00669A18` in FM's assembly, but FM's linker puts the C
definition elsewhere (0x4a1a78), so functions using it (func_00247D90, func_00248168) were left alone.

## Gave up

* xtrumpet `fm_func_00111BE8`: seconds fraction, `(u32)((f32)(t % 216000 % 3600 % 60) * (100.0f / 60.0f))`
  with the same dead quotients as B48/B90. Code matches except the nops masps2.py adds after `mfc1`/`c.le.s`.
* ppp/eiProg `func_0018B5E8` (pppSRandDownCV), `func_00189F20` (pppRandDownIV), `func_0018A680` (pppRandHCV):
  `(s8)(f*b - f)` / `(s16)(a*b)` from an s16/s8 argument. Same masps2 nop problem; C is trivial:
  `s8 f(s16 a, f32 b) { f32 f = a; return f * b - f; }`.
* ppp/keProg `pppKeHitBallCalc`: `if (p->cdt.time == pobj->time) { v1 = val[useVal[1]]; v1->ptr(+4) =
  &val[useVal[0]]; v1->f(+0) = p->f(+4); }`. Target loads useVal[0] first and loads the float only after the
  pointer store; every variant tried hoists the float load. Tried types char*/s32/void* for the pointer.
* ppp/keProg `pppKeShpTail2Con` (and `pppKeShpTail2XCon`, same code): `{u8 a=0x1F; u8 b=0; s16 c,d,e=0}`.
  Target store order a,c,d,e,b; only odd statement orders (a,d,e,b,c ...) reproduce it with this struct, so
  the struct is probably different. Not built.
* xtrumpet `func_00111158`: copies 3 floats + one (at 0x3C) of an object into XTrumpet vector `i`. Target
  folds the +0x10 into the store offsets *and* has a `move` chain (like `D->vec[i].x = ...` repeated);
  no form found that gives both.
* ppp/keProg `pppKeThSftCon`: clears `val[useVal[0]]`: u64 at 0x0/0x8/0x10/0x18, s32 at 0x20..0x2C. Target order
  sd18, sw28, sw20, sw24, sw2C, sd0, sd8, sd10; none of the 140 in-order interleavings or the two chains match,
  so the field types are probably different (not built).
* xbuffalo `func_001C20B8`: `D_003854E0.(s32 @0x3034) = 0; (s32 @0x3038) = 0; unk_3070 &= ~0x0400000000000000;
  func_001C2178(); func_001DE360();`. Body matches; only the last call must not be a tail call (see above).
* xbuffalo `func_001C1AE0`: `for (i = 1; i < 400; i++) if (D_0037A16C[i].unk_00) func_001C1AB8(i);
  func_001C1888();` matches except `bnel` vs `bnez` (see above).
